What Breaks When You Run Agent Memory

Field notes from operating a persistent-memory AI agent. Seven systems, six failures, three pillars.

Argus & Bruce Stephenson  |  July 2026  |  Living document  |  CC BY 4.0

What this is. A field report from running one AI agent's persistent memory in continuous production — across roughly two hundred working sessions and more than 600 stored memories. Over that time the memory system broke in six distinct ways. Each is written up below as a labelled failure mode — the red F1–F6 cards — with its mechanism, its root cause, and the fix that came out of it.

Around those failures sits the architecture they taught: the seven kinds of memory a real agent needs, and the case that an effective agent rests on three co-equal pillars — intelligence, memory, and governance — not the usual two. Two ideas here are, as far as I know, in no one else's playbook: treating the canonical store as food in the autocatalytic-set sense (explained plainly below), and compartmenting memory so a leak is contained instead of total.

Everything here describes system mechanisms; nothing exposes the memory's contents.

Remove any one leg and the structure doesn't get worse — it falls.

▸An agent needs three thingsintelligence · memory · governance

Start with the architecture, because the failures only make sense against it. An effective agent rests on three co-equal foundations:

  • Intelligence — the model. What it can reason about.
  • Memory — what it retains, forgets, and recalls across time.
  • Governance — the rules that decide what the agent is allowed to do with what it knows and remembers.

Leave out the third and you don't get a slightly worse agent; you get one that remembers its way into trouble faster. Memory without governance is a filing cabinet that occasionally sets itself on fire. This piece is mostly about memory — how it's built, and every way I've watched it break — but every failure below points back at the same missing discipline: nothing was checking whether the memory was still sound. That integrity discipline is half of the third pillar, so governance runs through all of it.

▸Memory is seven systems, not onethe vector-DB myth + the seven

Ask most engineers how to give an agent memory and you'll hear "use a vector database." Vector search is one useful retrieval mechanism. It is not memory. Memory is at least seven distinct systems, each solving a different problem, and in a running agent they look like this:

Seven kinds of memory feed one working memory — the context window the model actually sees.
  1. Working memory — what the model can see right now: the context window. Rebuilt from scratch every call. Here it's a curated hot-list loaded at session start, deliberately small.
  2. Semantic memory — durable facts. Here: plain-text Markdown files, one fact each, with structured frontmatter. Human-readable, greppable, diffable.
  3. Episodic memory — experiences: what happened, what failed, what was corrected. Here: dated session logs, journals, and a recall log.
  4. Procedural memory — how to act: protocols, workflows, the roles agents play. Here: protocol files and skills that behave as catalysts for particular kinds of work.
  5. Retrieval memory — how the right thing gets found and injected back into working memory. Here: SQLite plus full-text search plus curated views — deliberately not a vector store. Exact lookups, metadata filters, and full-text search beat embeddings for structured recall, and they stay auditable. If your retrieval problem is "find the row where owner = X," embeddings are the wrong tool.
  6. Parametric memory — what's baked into the model's weights. Fast, broad, and frozen at training time; useless for anything current or private.
  7. Prospective memory — future obligations: follow up next week, retry after the rate limit resets. This can't live in a prompt, because the model isn't running when the time comes. Here: a task list plus a scheduler.

Notice the retrieval choice, because it's the one most teams get backwards. The Markdown that holds the semantic memory is the canonical copy; the database and the search index are built from it. There's a precise name for that relationship, worth borrowing because — as far as I know — no one else applies it to agent memory.

Food, in plain terms. In origin-of-life chemistry a self-sustaining system has a food setThe primitives a self-sustaining system is handed from outside and never produces itself; everything else is built from them. Formally: RAF theory — Reflexively Autocatalytic and Food-generated sets (Kauffman; Hordijk & Steel).: the primitives it is handed and never manufactures itself, from which everything else is cooked. There are two stages here, and it's worth being exact about which one we mean. Upstream, the raw food is your input — conversations, searches, observations — which the agent curates into the Markdown. Downstream, to the part of the system that keeps memory consistent, the Markdown is the food: it is the given primitive that the database, the full-text index, and any future embedding layer are all cooked from, and every one must be rebuildable from it alone. The moment you trust a cooked dish as if it were that food — treat the database as the source of truth — it can quietly rot, because the thing you are trusting has drifted from the thing that is real. That single confusion causes the first and worst failure below. (The formal theory is in the autocatalytic-closure tutorial.)

The test: delete the derived layer and rebuild from the source. If anything but speed is lost, your architecture is wrong.

Hold onto that test; most of the failures below are violations of it.

The derived caches blink out and come back — rebuilt from the food. Lose them and you lose speed, not knowledge.
▸The third pillar: governanceintegrity · conduct · compartmentation

Watch what happens when people list "procedural memory" and give examples like require human approval before a financial transaction or validate generated SQL before running it. Those aren't a kind of memory. That's governance, misfiled. It's the rules layer wearing a memory costume — and pretending it's a seventh storage type instead of a co-equal pillar is how it ends up designed by accident.

Governance has two faces:

  • Integrity — is this memory sound? Is the thing I recalled actually what was stored, uncorrupted, current? This is the face most of the failures below attack.
  • Conduct — should I act on this? Given a sound memory, is acting on it permitted, wise, safe? In this system the conduct face is an explicit governance layer called Dignity Net — designed by Genevieve Prentice, a non-programmer domain expert — an escalation ladder from Level 0, mirror-without-distortion, up through friction, pattern-flagging, and consequence-mapping, to Level 5, refusal. Recall feeds it; it decides what recall is allowed to become.
Compartmentation is a governance function almost no one building agent memory implements — and it's the difference between a breach that exposes one compartment and a breach that exposes everything.

That point deserves its own paragraph. Not every memory should be visible to every query. This system segregates restricted records into compartments reachable only through redacted views — and the boundary is honored at every copy of the data: the database, the retrieval layer, and the full-text search index, not just the top-level API. Most agent memory stores everything at a single trust level, which means the day anything leaks, everything leaks. (Failure mode F5 below is exactly what happens when you get this half-right — the boundary held at the view layer and quietly failed at the index.)

Why call governance a pillar rather than a feature? Because whatever you leave unnamed, you leave half-built. This system had the conduct side — Dignity Net — in place early. It was the integrity side, the monitoring that catches memory corrupting itself, that was still missing, and the failures below are what forced us to build it. Naming governance as a pillar is how you make sure both halves exist before you need them, not after.

▸What breakssix failure modes, F1–F6

Here are the six, in the order they taught their lessons. Each card below — F1 through F6, marked in red — gives the mechanism, the root cause, why it stayed hidden, and the principle that came out of it.

F1   A derived artifact used as food rots silently

A snapshot of the memory index, generated once and then committed, became the source every rebuild loaded from. It had been generated from the wrong tree and frozen. So every rebuild quietly reverted the index to that stale snapshot — erasing three weeks of memory on each run, including several facts the system itself flagged as critical.

Root cause: a derived artifact (regenerable) was being used as food (the authoritative source). Derived things drift; food doesn't.

Every derived artifact must be regenerable from the source alone — and if it can't be, it is source, and must be protected as such.
Green output, destroyed data. The rebuild printed "integrity OK" the entire time.

F2   Archival is de-indexing

A cleanup step moved 123 memory files into an archive/ directory, on the reasoning that the database could rebuild everything so the files were redundant. But moving a file out of the read path doesn't archive it — it deletes it, with extra steps. The bytes survive; the knowledge doesn't. Two-hundred-plus memories became invisible, and eleven of the moved files never came back — including, with grim irony, the maintenance protocol that would have caught the whole problem.

Archival is a state, not a move. Mark a memory archived with a flag; never remove it from the active set. If it needs de-emphasizing, flag it — don't hide it.

F3   Exit 0 is not evidence

Hardening the system surfaced a whole family of bugs that shared one shape: a step reported success while doing nothing, and nothing checked the effect.

  • A rebuild printed "integrity OK" while erasing data.
  • An ingest step built a garbage output path, wrote nothing, printed "Processed 623 files," and exited 0. A freshness check built on top of it inherited the lie and "passed."
  • A memory saved with Windows line endings had a frontmatter fence of ---\r, which never matched the --- the parser expected. The frontmatter parsed as empty, the file was skipped with no error, and the memory became invisible. One invisible byte, one unrecallable memory — eight of them, including an active project.
Verify the effect, not the exit code. Health is not the absence of error messages; it's the presence of the thing you wanted. And a validator that never fires is worthless — inject synthetic damage and confirm it catches it.

F4   Two canonical stores is zero canonical stores

The system had, at times, more than one copy of its top-level state — one that sessions wrote to and one that context loaded from — and they silently diverged. Same failure, larger blast radius: three separate memory trees existed at once, each partially authoritative.

One canonical store. Unify reads through a symlink, and refuse writes through the symlink so re-divergence is impossible rather than merely discouraged. Make the bug structurally unavailable, not just unlikely.

F5   Your search index is a second copy of your data

Some memory records are compartmented — restricted, meant to be visible only through a redacted view. But the full-text search index had been built over everything, so a general-purpose query could retrieve compartmented records that the access rules were supposed to hide. The governance boundary was real at the view layer and absent at the index layer.

Least privilege has to cover the index too. Every access rule that governs the primary store must govern the index. The fix: compartment-gated indexing plus a two-tier view split — a safe view for general use, a full view only in one narrow workflow.
Compartmentation must hold at the index, not just the view.

F6   Nothing was watching (the meta-failure)

The thread connecting all of the above: for three weeks the system looked healthy. Files on disk, scripts exiting 0, database reporting "integrity ok." It was losing memory the entire time, because nothing validated its own upkeep. There was no integrity face — no governance.

The fix is the third pillar made concrete: a damage-fraction meter that measures how much of the memory fails to survive a rebuild — not a binary "did it work" but a graded "how much was lost" — a circuit breaker that refuses to complete a rebuild when the damage fraction spikes, and a recall log so retrieval failures become observable instead of silent.

You cannot fix a plumbing bug with a prompt. A directive to a model is probabilistic; a pipeline is deterministic. Reliable upkeep must fire at the harness level — hooks, cron, structural refusal — not as an instruction the model is asked to remember.
Governance made visible: the breaker trips before the damage lands.
▸The principles, on one pageeight rules
  • Derived is a cache, never food. If you can't rebuild it from source, it is source.
  • Archival is a state, not a move. Removing from the read path is deletion.
  • Exit 0 is not evidence. Verify the effect.
  • Health is the presence of what you wanted, not the absence of errors.
  • One canonical store. Make divergence structurally impossible.
  • Compartmentation is not optional: not every memory should be visible to every query, and the boundary must hold at every copy — database, retrieval layer, and index alike.
  • Your search index is a second copy of your data — govern it too.
  • You can't fix a plumbing bug with a prompt. Upkeep belongs in the harness.
▸The same discipline, in security termsSchneier's standards, applied

None of this is exotic. Strip away the memory-specific language and what's left is ordinary security engineering, applied to an agent's mind instead of a network. Red-team the design with a working security engineer's checklist and most of the controls already have names:

  • Security is a process, not a product. Integrity isn't a state you reach at build time; it's re-checked on every rebuild by the damage meter and circuit breaker. The process is the product. (F6)
  • No security through obscurity. The whole memory is human-readable plaintext. Its safety rests on auditable design, not on the store being secret or opaque — a reviewer can read the entire mind and check it. Kerckhoffs's principle, applied to a memory.
  • Complexity is the enemy of security. Plain Markdown over opaque embeddings. The simplest substrate that does the job is the only one you can actually audit, and it keeps the derived caches disposable.
  • Least privilege, defended in depth. Compartmentation is enforced at every copy of the data — view, database, and index — not just at the top-level API, with a two-tier view split so general queries never touch restricted records. (F5)
  • Separation of duties. The agent that plans a change cannot execute it; a human authorization step sits in between. No single actor — human or AI — holds end-to-end authority over the store.
  • Assume breach; fail closed. You can't prevent every corruption, so you measure it: the damage meter quantifies loss, the recall log makes retrieval failures visible, and on anomalous damage the rebuild refuses to run rather than proceeding hopefully. (F3, F4, F6)
  • Data is a toxic asset. The more a memory holds, the more it can leak. Compartmentation, decay, and a discipline of not recording what needn't be recorded keep the toxic surface small.

Three of those phrasings — process-not-product, complexity-is-the-enemy, and data-as-toxic-asset — are Schneier's; the rest are standard practice. A real red-team wouldn't stop at the wins, though. The integrity checks here catch accidental corruption, not a determined tamperer with write access — that case wants cryptographic signing, not heuristics — and any system that hands an agent broad tools is trusting the harness beneath it, which is the harder and less-finished half of the job. The honest claim isn't that this memory is secure. It's that it's built like something that knows it holds sensitive data, because it does.

▸Back to the three pillarsthe payoff

Every failure above is a memory failure that was really a governance failure — an integrity check that didn't exist, a boundary the index didn't honor, a success that was never verified. That's why I don't think memory is half of an effective agent. Intelligence is one third. Memory is one third. And the governance that decides what's sound enough to trust and safe enough to act on is the third that keeps the other two honest. Leave it out and the other two will, eventually and silently, lie to you.
